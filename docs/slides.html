Foundation

What is S2 Geometry?

Google's open-source spherical indexing system used in Maps, BigQuery, and Spanner.

1. The Problem with 2D Coordinates

  • Standard lat/lng $(x, y)$ coordinates are continuous, 2D spherical floats.
  • Distributed databases cannot natively index 2D points using standard B-Trees without expensive 2D spatial engine plugins.
  • Searching nearby locations without an index requires a full table scan of all rows across all splits.

2. The S2 Solution

  • Cube Face Quad-Tree: Projects Earth's sphere onto 6 cube faces and recursively subdivides them up to 30 levels.
  • 1D Hilbert Curve: Maps 2D cells onto a 1-dimensional 64-bit integer (S2CellId).
  • Spatial Locality: Points near each other on Earth map to contiguous 1D integers, allowing standard Spanner B-Tree secondary indexes to execute spatial searches.

Execution Flow

How the Query Executes in 3 Steps

From customer coordinates to top-10 closest entities via Spanner Graph.

Step 1: Cell Resolution

  • Customer input: (39.7459, -75.5466).
  • Client calculates the parent S2 cell at Level 8 (~50 km metro radius).
  • Produces token '89c6f' (signed INT64 -8518857762334048256).

Step 2: Spanner Index Seek

  • Hits secondary index IndexLocationS2TokensByToken on table LocationS2Tokens.
  • Performs an exact point lookup for S2Token = @s2_token.
  • Instantly prunes 100K+ rows down to only ~50 candidate location IDs.

Step 3: Graph + Ranking

  • Traverses LEIGraph via GRAPH_TABLE: (Entity)-[HAS_LOCATION]->(Location).
  • Enriches entities with legal names and status.
  • Evaluates exact Haversine distance on candidates and returns LIMIT 10.

Strengths

Pros of the S2 + Spanner Graph Approach

Key architectural advantages for enterprise-scale entity graphs.

High Performance & Scalability

  • Sub-Millisecond Candidate Pruning: B-Tree point index seek replaces $O(N)$ full table scans with $O(\log N)$ seeks.
  • Native Spanner Compatibility: Runs on standard Spanner tables and secondary indexes without requiring specialized GIS extensions.
  • Seamless Graph Integration: Spanner GRAPH_TABLE combines spatial indexes with multi-hop graph relationship traversals in a single query.

Flexibility & Efficiency

  • Multi-Resolution Hierarchy: Query radius can be adjusted on the fly simply by changing S2 levels (Level 6 = ~200 km, Level 8 = ~50 km, Level 10 = ~12 km).
  • Minimal CPU & Memory Footprint: Costly Haversine trigonometric functions are evaluated on dozens of candidate rows rather than hundreds of thousands.

Trade-Offs

Cons & Considerations

Inherent trade-offs of discrete spatial partitioning and mitigation strategies.

Edge Cases & Ingestion Overhead

  • Boundary / Edge Effect: If a customer coordinate lies near a cell border, a closer entity across the border in an adjacent cell could be missed if querying only 1 token.
  • Storage Amplification: Indexing multiple S2 levels per address (e.g. 6, 8, 10, 12, 14) multiplies index row count in LocationS2Tokens.
  • Client / Ingestion Dependency: Ingestion pipelines must compute S2 cell IDs prior to insertion into Spanner.

Mitigations & Best Practices

  • 9-Cell Neighbor Expansion: For border-critical applications, query the center S2 token plus its 8 adjacent neighbors (t.S2Token IN (...)).
  • Curated Level Selection: Store only 3–4 practical levels (e.g. Levels 6, 8, 10) instead of all 30 levels to balance storage vs. precision.
  • Hybrid Search: Combine with Spanner Full-Text Search (SEARCH_SUBSTRING, SEARCH_NGRAMS) for comprehensive filtering.

Conclusion

Summary & Recommendation

When and how to deploy S2 indexing on Cloud Spanner Graph.

When to Use

  • Global entity datasets (LEI, corporate hierarchies, supply chains, banking networks).
  • High-QPS proximity search combined with ownership and relationship graph queries.
  • Horizontally scalable environments where traditional GIS plugins introduce scaling bottlenecks.

Recommended Production Configuration

  • Primary Spatial Index: Level 8 (~50 km) for metro search, Level 10 (~12 km) for city search.
  • Secondary Text Index: Tokenlist search index on legal name (name_FullText, name_Tokens).
  • Graph Engine: Spanner Property Graph (LEIGraph) with GRAPH_TABLE for unified declarative querying.
